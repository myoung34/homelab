# terraform/talos

Talos node config for the cluster. Read this before any change here: a Talos
or Kubernetes upgrade, a template edit, or adding or removing a node.

## How config is built

`data "talos_machine_configuration"` generates each node's base config for
`local.talos_version`. Terraform then patches it with
`local.controlplane_patches` or `local.worker_patches`, which render the files
in `templates/`.

`talos_version` is the config *contract*, not only the installer tag. It picks
the generator's defaults and its document format, so bumping it changes the
base config every node gets, even with no template edits.

## Validate every change

Run `terraform/talos/validate.sh` before opening a PR. It renders every
node's config exactly as terraform builds it and runs
`talosctl validate --strict` from the matching Talos release. It needs
terraform, curl and python3, and no Vault or cluster access.

CI runs the same script on every push that touches this directory
(`.github/workflows/talos.yaml`, check name "Validate Talos config"). A red
check means Talos would reject the config at `terraform apply`. If you can't
run the script yourself, read the PR's check result before calling it ready.

A green check proves the config is valid, not that it still does what it did.
See "Keep every behaviour".

## Upgrade Talos and Kubernetes

1. Upgrade the nodes first, still on the old config:
   `talosctl upgrade --image <schematic>:<version>` on every node. An older
   node rejects config documents it doesn't know (see the comment in
   `worker.tf`), so `terraform apply` has to wait.

   On cluster41 the drain always fails, because Longhorn's instance-manager
   PDB guards the only replicas of the ollama volumes. talosctl 1.14+ then
   skips the reboot and leaves the node cordoned on the old version. Once
   only DaemonSet pods and that instance-manager are left on the node
   (`kubectl get pods -A --field-selector spec.nodeName=cluster41`), re-run
   the same upgrade with `--drain=false`.
1. Upgrade Kubernetes with `talosctl upgrade-k8s --to <version>`. Take the
   version from the "Component Updates" section of that Talos release's notes
   and state the mapping in the PR.
1. In one PR, bump `talos_version` and `kubernetes_version` in `locals.tf`,
   migrate the templates, and update the pins listed below. Apply it as in
   "Apply without state".

Every apply regenerates the whole config from the new contract, so the
target is what the new version generates, not what a node runs today:

- Release-note lines like "upgraded clusters keep the old behaviour" describe
  an in-place upgrade and don't apply here.
- An upgrade never rewrites a node's config. Talos changes it only through
  `apply-config`, `patch` or `edit`, so an upgraded node keeps its old shape,
  and `talosctl get mc` returns what you already have.

Take the target shape from a config generated by the target release's
talosctl, and diff each rendered template against it. The homelab-agent's
`/opt/talosctl/talosctl` is the cluster's current version, so download the
target's binary first:

```sh
curl -fsSL -o talosctl \
  https://github.com/siderolabs/talos/releases/download/<version>/talosctl-linux-amd64
chmod +x talosctl
./talosctl gen config ref https://x:6443 -o "$TMPDIR/ref"
```

### Migrating templates to a new version

Run these in order. Each step ends on a command whose output decides it.

1. Check for fields with no replacement document before editing anything:

   ```sh
   grep -rnE '^\s+extraMounts:' terraform/talos/templates/
   ```

   Any hit means stop and ask Mark how to migrate that template, then wait
   for his answer. Do the same for any other field step 2 finds no document
   for. Example: 1.14 has no replacement for `.machine.kubelet.extraMounts`,
   so Mark chose to drop the Longhorn templates' `/var/lib/longhorn` kubelet
   binds when moving to 1.14 (canary-tested on one node first).

1. Rewrite every moved v1alpha1 field in `templates/` as its typed document.
   A deprecated field and its replacement document can't both be set. Take
   each document's `kind` and field names from the target version's
   document map, saved to disk so you can grep it:

   ```sh
   curl -fsSL -o docmap.html \
     https://docs.siderolabs.com/talos/<minor, e.g. v1.14>/reference/configuration/document-map
   grep -c '<code>SysctlConfig</code>' docmap.html   # 0: no such kind
   ```

   Run that grep for every `kind:` you write; each must print 1 or more.
   Grep the `<code>` form: the page also names v1alpha1's internal types
   (`*TimeConfig`, `*KernelConfig`, `*LoggingConfig`), which are not
   documents. A kind from memory is a guess.

1. Read the release's "What's New" for documents the generator now emits by
   default, and name each one in the PR body with whether you pin it.
   Example: 1.14 adds `SecurityProfileConfig` with `workloadIsolation: true`,
   which blocks pods from the host iscsid that Longhorn's v1 engine uses.

1. Run `terraform/talos/validate.sh` (see "Validate every change"). It passes
   when it exits 0 with an `ok` line per node; any `FAIL` line is a
   rejection. `talosctl validate --strict` rejects unknown kinds and
   conflicting fields, so a `FAIL` means step 2 is wrong. Fix it and run
   again. The PR is ready only when this run passes and the "Validate Talos
   config" check on the PR is green.

## Apply without state

This root keeps no Terraform state. Talos already holds each node's real
config, and a local `terraform.tfstate` only went stale (it once tracked 1 of
10 nodes). So every plan lists every node as "will be created", and every
apply pushes each node's full config with `apply-config --mode auto`, which
reboots a node if the change needs it. Read the change from the nodes, not
the plan:

```sh
cd terraform/talos
s=$(mktemp -d)   # throwaway state and plan; holds machine secrets
terraform plan -state="$s/tfstate" -out="$s/plan"
terraform show -json "$s/plan" | python3 -c '
import json, pathlib, sys
for rc in json.load(sys.stdin)["resource_changes"]:
    if rc["type"] == "talos_machine_configuration_apply":
        mc = rc["change"]["after"]["machine_configuration"]
        pathlib.Path(sys.argv[1], rc["index"] + ".yaml").write_text(mc)
' "$s"
for f in "$s"/*.yaml; do
  talosctl -n "$(basename "$f" .yaml)" apply-config --dry-run --mode auto -f "$f"
done
```

Run the dry runs with a talosctl matching the nodes' Talos version. Each must
say "without a reboot" and show only the diff you meant to make. Then apply
that exact plan and delete the directory:

```sh
terraform apply -state="$s/tfstate" "$s/plan"
rm -rf "$s"
```

## Keep every behaviour

Each block in `templates/` exists for a reason, usually written in the
comment above it. For example, the cluster41 watchdog in
`bare-metal.yaml.tmpl` came out of a real hard lock. Carry every block across
a change, migrating its format where needed. When a block is removed or
renamed, name it and its replacement in the PR body. A block that disappears
without a named replacement is a regression, even when validation passes.

## Pins that follow `talos_version`

Leave `rpi_overlay_sha`, `rpi5_overlay_sha` and `bare_metal_sha` alone. A
schematic ID covers only the extensions and overlay, not the Talos version;
`locals.tf` adds the version as the image tag. Regenerate one only when its
schematic YAML changes.

Grep the repo for the old version string, then update or justify every hit.
Known pins:

- `k8s/prod/kagent/homelab-agent.yaml`: the `ghcr.io/siderolabs/talosctl`
  image volume
- `k8s/prod/workflows/etcdsnapshot.yaml`: the talosctl download URL
- `k8s/prod/workflows/talos.yaml`: the talosctl download URL
- `README.md` in this directory: the upgrade example
